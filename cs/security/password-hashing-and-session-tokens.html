🔐Password hashing and session tokens

How a web app checks your password without ever storing it, then remembers you with a signed token kept in a protected cookie.

beginnercs2026-11-27

💡The idea

Logging in has two jobs. First, check the password: the server stores only a hash of it, a scrambled fingerprint that cannot be turned back into the password. Second, remember who you are on every later request: the server gives the browser a signed token (a JWT) that says "this is user 42, valid until next week". The browser keeps it in a cookie and sends it back automatically.

💡 Think of it like this

At a festival, the guard checks your ID once at the gate (the password). Then you get a wristband with a hologram (the token). For the rest of the week, staff just look at the wristband. They can't easily fake the hologram, but they also can't take back a wristband before it expires.

📖Key words

Hash
A one-way function: easy to compute from the password, impossible to reverse.
Salt
A random value mixed into each password before hashing, so two equal passwords give different hashes.
Argon2
A password-hashing algorithm built to be slow and memory-hungry, so guessing millions of passwords is expensive.
JWT (JSON Web Token)
A small text token in three parts, header.payload.signature, that the server signs so nobody can change it.
User enumeration
An attack that finds out which emails have an account by watching how the server answers.

⚙️How it works

  1. Sign up: Argon2 picks a random salt, hashes salt + password, and stores one string like $argon2id$…salt…hash. The salt is not secret; it just makes every hash unique, so attackers can't use precomputed tables.
  2. Log in: Argon2 re-hashes the typed password with the stored salt and compares. Each try takes a noticeable fraction of a second on purpose: nothing for you, but painful for an attacker testing billions of guesses.
  3. Unknown email: the server still checks the password against a dummy hash. A wrong email then takes as long as a wrong password, and both get the same message: "Wrong email or password".
  4. Create the token: the payload holds sub (subject: the user id) and exp (expiry time). The server signs header + payload with HS256 and a secret only it knows.
  5. Read the token: on each request the server recomputes the signature. Wrong secret, changed payload, missing exp, expired, or algorithm none (no signature at all): rejected with 401.
⚠️ Common mistake

Base64 only turns bytes into safe text. Anyone can decode a JWT and read it. The signature stops changes, not reading.

🔍Example

In the habit tracker, all of this lives in api/app/security.py (shortened here):

_hasher = PasswordHasher()  # argon2id; adds a random salt by itself
_DUMMY_HASH = _hasher.hash("not-a-real-password")

def verify_password(password, password_hash):
    try:  # no user? check the dummy hash anyway (same time), then refuse
        return _hasher.verify(password_hash or _DUMMY_HASH, password) and password_hash is not None
    except (VerificationError, InvalidHashError):
        return False

def create_token(user_id):
    now = datetime.now(UTC)
    payload = {"sub": str(user_id), "iat": now, "exp": now + timedelta(days=7)}
    return jwt.encode(payload, settings.jwt_secret, algorithm="HS256")

# reading: only HS256 is accepted, and exp + sub must be present
jwt.decode(token, secret, algorithms=["HS256"], options={"require": ["exp", "sub"]})

The token then goes into a cookie (routers/auth.py). The test test_me_rejects_forged_expired_and_orphan_tokens builds a token signed with another secret, an expired one, one with no exp, an unsigned none one, and one for a deleted user: all get 401. In production, config.py refuses to start with the dev secret or a secret shorter than 32 characters.

⚖️Why use it

✅ Advantages

  • A stolen database gives hashes, not passwords, and each guess costs real time.
  • The server needs no session table: the signature alone proves the token is real.
  • The cookie flags block the most common ways to steal or misuse the token.

⚠️ Limits

  • One 7-day token can't be revoked early: if it's stolen, it works until exp, even after logout.
  • Anyone who learns the secret can forge tokens for any user.

🔀Other ways

Access + refresh tokens: a short access token (about 15 min) plus a long refresh token stored in the database, which can be deleted to log someone out everywhere.
Server-side sessions: the cookie holds a random id and the server keeps a session table; revoking is just deleting a row.
bcrypt or scrypt: older slow password hashes; still fine, but Argon2id is today's recommended choice.

🎯Quiz

  1. A hash is one-way: from the hash, you cannot get back the _____.

    Answer

    Password. The server can only hash a new guess and compare the two hashes; it never needs the original password.

  2. Is it true that encrypting passwords with a secret key is as safe as hashing them?

    Answer

    No, false. Encryption can be undone with the key. If an attacker steals the key along with the database, every password is revealed. A hash has no key to steal.

  3. What is a salt in password hashing?

    1. A secret key the server uses to decrypt passwords
    2. A rule forcing users to pick long passwords
    3. A random value mixed into each password before hashing
    4. A second password the user must remember
    Answer

    C. The salt is random per user and stored next to the hash. A is tempting, but a salt is not secret and nothing is ever decrypted.

  4. Is it true that two users with the same password get the same Argon2 hash?

    Answer

    No, false. Each user gets a different random salt, so the hashes differ. An attacker can't spot shared passwords or use precomputed tables.

  5. Why is a password-hashing algorithm like Argon2 slow on purpose?

    Answer

    A fraction of a second doesn't bother a real user who logs in once, but an attacker trying billions of guesses on a stolen hash would need years. Slowness makes brute force too expensive.

  6. Why should a login form say "wrong email or password" instead of "no account with this email"?

    Answer

    A precise message tells an attacker which emails have an account (user enumeration). They can then target those accounts with password guesses or phishing.

  7. Why does a server check a dummy hash when the email does not exist?

    1. So a wrong email takes as long to answer as a wrong password
    2. To create a new account for that email
    3. To store the wrong password for later analysis
    4. To make the server faster for real users
    Answer

    A. Without it, an unknown email would be answered instantly while a known one waits for Argon2, and that time difference would reveal which emails exist. D is wrong: it adds work, it doesn't save any.

  8. A JWT has three parts separated by dots: header, payload and _____.

    Answer

    Signature. The signature is computed from the header, the payload and the server's secret, so any change to them breaks it.

  9. Is it true that anyone who gets a JWT can read its payload?

    Answer

    Yes, true. The payload is only base64-encoded, not encrypted. That's why it holds a user id and an expiry, never a password or other secret.

  10. What does a valid HS256 signature on a token prove?

    1. That the payload is encrypted
    2. That the token was made with the server's secret and not changed since
    3. That the user typed the right password just now
    4. That the token can never expire
    Answer

    B. Only someone who knows the secret can produce a matching signature. A is the classic mix-up: signing protects against changes, not against reading.

  11. The JWT field that says when the token stops being valid is called _____.

    Answer

    exp. It holds the expiry time. The server rejects tokens past that time, and in the example it also rejects tokens that have no exp at all.

  12. Why must a server refuse tokens that use the "none" algorithm?

    Answer

    A "none" token has no signature, so anyone could write any user id in it and log in as that user. The server should accept only the one algorithm it uses, like HS256.

  13. Which cookie flag stops JavaScript on the page from reading the token?

    1. Secure
    2. SameSite=Lax
    3. Max-Age
    4. HttpOnly
    Answer

    D. HttpOnly hides the cookie from scripts, so an XSS bug can't steal it. A is tempting, but Secure only controls HTTPS, not who can read it.

  14. Is it true that SameSite=Lax stops the browser from sending the cookie on a form POST from another website?

    Answer

    Yes, true. That blocks CSRF: an evil site can't make your browser submit a logged-in request to the app behind your back.

  15. Is it true that the Secure cookie flag encrypts the content of the cookie?

    Answer

    No, false. Secure only means the cookie travels over HTTPS, so nobody on the network sees it. The cookie itself is unchanged.

  16. What is the main downside of one long-lived token, and how do refresh tokens help?

    Answer

    A stolen long token works until it expires, and the server can't cancel it. With refresh tokens, the access token lives only minutes, and the long refresh token is stored on the server, where it can be deleted to revoke access.

🔎Things worth noticing

  • Sign-up still enumerates users: /auth/signup answers 409 "An account with this email already exists", so the careful login message can be bypassed. Common fixes: rate limiting, or a neutral "check your email" flow.
  • Logout only deletes the cookie in the browser. A copy of the token made before still works until exp: this is the revocation trade-off in practice.
  • Argon2 settings may get stronger in future library versions; check_needs_rehash at login can upgrade old hashes.
