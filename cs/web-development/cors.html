🌐CORS: how browsers let one website call another

CORS is the set of rules a browser follows to decide if a web page may read the answer from a server on another address.

beginnercs2026-11-27

💡The idea

By default, a browser does not let a page read answers from a different origin (another site address). This rule is the same-origin policy. It protects you: a random page you visit can't quietly read your bank's data using your login. CORS (Cross-Origin Resource Sharing) is how a server says "this other site is allowed to read my answers".

💡 Think of it like this

The browser is a careful parent passing notes between kids. It delivers a note to another house, but it only hands the reply to the child if the reply says "yes, this child may read it".

📖Key words

Origin
The scheme + domain + port of a URL, like https://example.com:443; change any part and it is a different origin.
Same-origin policy
The browser's default rule: a page may only read responses from its own origin.
Header
A small labelled piece of information sent with a request or a response.
Access-Control-Allow-Origin
The response header in which the server names the origin that may read the answer.
Preflight
A test request with the method OPTIONS that the browser sends first, to ask "may I send this?".

⚙️How it works

  1. The page wants to call another origin. The browser adds an Origin header saying where the page comes from.
  2. For "non-simple" requests (for example a POST with JSON), the browser first sends a preflight OPTIONS request.
  3. The server answers. If it trusts that origin, it adds Access-Control-Allow-Origin: <that origin>.
  4. The browser compares. If the header matches, it sends the real request and gives the reply to the page. If not, it blocks and shows a CORS error in the console.
⚠️ Common mistake

CORS is not a security wall for the server. Tools like curl are not browsers, so they ignore CORS completely. Anyone can still call your API directly. Protect it with validation, rate limits or authentication.

🔍Example

Your contact form on Vercel posts JSON to your FastAPI server on Render: two origins. The API lists the allowed origins:

# api/app/main.py
app.add_middleware(
    CORSMiddleware,
    # read from the ALLOWED_ORIGINS env var, comma-separated
    allow_origins=[o.strip() for o in os.getenv("ALLOWED_ORIGINS", DEFAULT_ORIGINS).split(",") if o.strip()],
    allow_methods=["POST"],          # only POST is allowed cross-origin
    allow_headers=["Content-Type"],  # the form sends JSON
)

# api/tests/test_contact.py: the preflight check
ok  = client.options("/contact", headers={"Origin": SITE, "Access-Control-Request-Method": "POST"})
bad = client.options("/contact", headers={"Origin": "https://evil.example", ...})
assert ok.headers.get("access-control-allow-origin") == SITE
assert "access-control-allow-origin" not in bad.headers

At first, ALLOWED_ORIGINS held the wrong Vercel address. The server was fine (curl worked), but its preflight answer never named the real site, so the browser would have blocked the form. The test now fakes a preflight from the right and a wrong origin to catch this.

⚖️Why use it

✅ Advantages

  • Lets a front end and an API live on different domains safely.
  • Protects users: other sites can't read your API's answers through their browser.

⚠️ Limits

  • Does nothing against curl, scripts or bots.
  • Easy to misconfigure: one wrong letter in the origin breaks the site.

🔀Other ways

Same origin: serve the API under the site's own domain (e.g. /api), so CORS is never needed.
Proxy: the site's own server forwards the request to the API; server-to-server calls ignore CORS.
Allow every origin (*): simple, fine for public data, but any site can then read the answers.

🎯Quiz

  1. Which change turns a URL into a different origin?

    1. Changing the path, like /about to /contact
    2. Adding ?page=2 at the end
    3. Changing http to https
    4. Adding #top at the end
    Answer

    C. An origin is scheme + domain + port, so changing the scheme changes the origin. The path (A) is not part of the origin.

  2. The browser rule that a page may only read responses from its own origin is called the _____ policy.

    Answer

    Same-origin. It is the default; CORS is the way a server relaxes it for chosen sites.

  3. Why do browsers have the same-origin policy at all?

    Answer

    To protect users: without it, any page you visit could use your logged-in browser to read your data from other sites, like your bank or email.

  4. Is it true that the server is the one that blocks a cross-origin request when CORS fails?

    Answer

    No, false. The server only sends (or doesn't send) permission headers. The browser reads them and blocks the page from getting the reply.

  5. What is a preflight request?

    1. A request that logs the user in first
    2. An OPTIONS request the browser sends first to ask if the real request is allowed
    3. A request the server sends to the browser before loading a page
    4. A copy of the request kept in case the first one fails
    Answer

    B. Before a non-simple request (like a POST with JSON), the browser asks permission with OPTIONS. It has nothing to do with logging in (A).

  6. Is it true that every cross-origin request starts with a preflight?

    Answer

    No, false. Simple requests, like a plain GET with no special headers, are sent directly. The browser still checks the Allow-Origin header on the reply.

  7. The server names the origin allowed to read its reply in the _____ header.

    Answer

    Access-Control-Allow-Origin. If it is missing or names another origin, the browser hides the reply from the page.

  8. If the allowed origin is set to the wrong address, what happens when the real site calls the API?

    1. The server crashes
    2. The request works, CORS is only a warning
    3. The server returns 404 Not Found
    4. The browser blocks the call, even though the server works
    Answer

    D. The server answers normally but without a matching Allow-Origin header, so the browser refuses. This is exactly what can happen with a wrong deployment address.

  9. Why can curl call an API that the browser blocks with a CORS error?

    Answer

    CORS is enforced by browsers only. curl is not a browser, so it never checks the Allow-Origin header and simply shows the reply.

  10. Is it true that CORS stops attackers from sending requests to your API?

    Answer

    No, false. Anyone can call the API with curl or a script. Real protection needs input validation, rate limits or authentication on the server.

🔎Things worth noticing

  • The form's "wake up" call to /health is a simple GET with no preflight. The request reaches the server even if the browser later hides the reply, which is why it can still wake Render up. CORS blocks reading, not sending.
  • Origins must match exactly: no trailing slash, right scheme. https://site.vercel.app/ would not match.
