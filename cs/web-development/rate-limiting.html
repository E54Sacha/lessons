🚦Rate limiting

How a server says "slow down": it counts each visitor's requests and refuses the extra ones.

beginnercs2026-11-27

💡The idea

A server that anyone can call can also be flooded: a bot could send 10,000 contact messages in a minute. Rate limiting means counting how many requests each visitor made recently and refusing the ones above a limit. A refused request gets the HTTP answer 429 Too Many Requests. Your portfolio allows 5 messages per visitor per 10 minutes, and 30 per hour for everyone together.

💡 Think of it like this

A free-sample stand at the supermarket: each person gets at most 5 samples, and the stand only has 30 per hour in total.

📖Key words

Key
What the server uses to tell visitors apart (user account, IP address…). Requests with the same key share one counter.
Window
The stretch of time the limit applies to, like "the last 10 minutes".
Fixed window
Counters reset at set times (every hour on the hour).
Sliding window
The server remembers the time of each request and only counts the ones from the last 10 minutes, measured from now.
Race condition
A bug where two things running at the same moment interfere, so the result depends on who goes first.

⚙️How it works

  1. Pick a key. Your code uses the visitor's network: all addresses that share the first 3 numbers of an IPv4 address (a "/24") count as one visitor, so hopping to a neighbour address doesn't reset the limit.
  2. Find the real IP safely. Behind a proxy (a middle server, here Render's), the address arrives in the X-Forwarded-For header. The visitor can write fake entries at the start; only the last one, added by the proxy, is trusted.
  3. Forget old requests. Drop timestamps older than the window, then count what is left.
  4. Check and count in one step, inside a lock (a "one at a time" door), before sending.
  5. Keep memory bounded. At most 10,000 visitors are remembered; the oldest are forgotten first.
⚠️ Common mistake: check, then count

If you check first and count only after sending the email, 12 parallel requests can all pass the check before any of them is counted. This is a race condition (also called TOCTOU: "time of check, time of use").

🔍Example

The heart of your limiter (slightly shortened):

def reserve(key):
    with _lock:                         # only one request in here at a time
        now = time.monotonic()
        reason = limit_reason(key, now)  # check...
        if reason is None:
            record(key, now)             # ...and count, in the same step
        return reason, now

def limit_reason(key, now):
    hits = _hits.get(key)                # this visitor's timestamps
    if hits is not None:
        _expire(hits, now, RATE_WINDOW)  # drop the ones older than 10 min
        if len(hits) >= RATE_LIMIT:
            return "visitor"             # becomes a 429
    ...                                  # same check for the global limit

If sending fails, the message still counts, so retrying can't bypass the limit. The slot is given back only when the failure is the server's fault (email not set up).

⚖️Why use it

✅ Advantages

  • Stops spam floods and protects paid quotas (your free email allowance).
  • Keeps one visitor from hogging the server.

⚠️ Limits

  • People sharing one network (an office, a school) share one limit.
  • A global cap can be used up by an attacker, blocking honest visitors too.

🔀Other ways

Token bucket: each visitor has a bucket of tokens that refills slowly; each request spends one. It allows short bursts but limits the average.
Fixed window counter: one number per visitor, reset on a schedule. Uses less memory, but allows bursts at the reset.
Shared store (Redis): keeps counters outside the app, so several servers share them and restarts don't erase them.

🎯Quiz

  1. A server refuses a request that is over the limit with the HTTP status code _____.

    Answer

    429. It means "Too Many Requests" and tells the client to slow down and try again later.

  2. Why would a public contact form need a rate limit?

    Answer

    Without one, a bot could send thousands of messages, flooding the inbox and using up any paid or free quota. The limit caps how much damage one sender can do.

  3. What does the key of a rate limiter decide?

    1. How long the time window lasts
    2. How many requests are allowed
    3. Which requests share the same counter
    4. Which error message is shown
    Answer

    C. The key (an account, an IP address, a network) groups requests: the same key means the same counter. B is the limit itself, not the key.

  4. The limit is 3 messages per 10 minutes, with a sliding window. Messages were sent at minutes 0, 2 and 4. When can the next one go through?

    1. At minute 5
    2. Just after minute 10
    3. At minute 14
    4. At minute 20
    Answer

    B. Just after minute 10, the message from minute 0 leaves the 10-minute window, so only 2 are counted. C is tempting, but you don't wait for all three to expire, only the oldest.

  5. Is it true that a fixed window can let through almost twice the limit in a short time?

    Answer

    Yes, true. A visitor can use the full limit just before the reset and again just after it. A sliding window avoids this.

  6. In a token bucket, each request spends one _____, and they refill slowly over time.

    Answer

    Token. When the bucket is empty, requests are refused until it refills.

  7. Is it true that a token bucket forbids all bursts of requests?

    Answer

    No, false. A full bucket allows a short burst (spend all tokens at once); it only limits the average rate over time.

  8. Why group visitors by network instead of by their exact IP address?

    Answer

    One person often controls many addresses in the same block and can switch between them. Grouping by network stops them from getting a fresh limit each time.

  9. Is it true that a server can safely trust the first address in the X-Forwarded-For header?

    Answer

    No, false. The visitor can write anything at the start of that header. Only the entry added by your own proxy (the last one, on Render) can be trusted.

  10. Why must the memory of a rate limiter be bounded?

    1. To make the code easier to read
    2. Because limits must reset every hour
    3. Because a dictionary cannot hold many entries
    4. Because requests from many addresses could fill memory until the server crashes
    Answer

    D. Every new key adds an entry. Without a maximum, an attacker using many addresses could grow memory forever. C is wrong: dictionaries can grow very large, which is exactly the danger.

  11. A bug where parallel requests interfere and the result depends on who goes first is a race _____.

    Answer

    Condition. In a rate limiter, several requests can all pass the check before any of them is counted.

  12. How does a lock fix the race condition in a rate limiter?

    Answer

    It lets only one request at a time check the counter and count itself, in one step. The next request then sees the updated count, so no extra request slips through.

  13. Why should a message that failed to send still count against the limit?

    1. So retrying can't be used to send unlimited requests
    2. Because failed requests are always attacks
    3. To make the error message shorter
    4. Because the server cannot tell it failed
    Answer

    A. Otherwise someone could retry forever. Also, a timeout may have delivered the email anyway. B is too strong: honest sends fail too.

  14. Is it true that a global limit can block honest visitors if an attacker uses it up?

    Answer

    Yes, true. The global cap is shared by everyone. It protects the inbox and quota, but the price is that a flood can make the form unavailable for a while.

🔎Things worth noticing

  • The counters live in memory, so they are erased whenever the server restarts (free Render servers sleep and restart often). With two servers, each would have its own counters.
  • Trusting the last X-Forwarded-For entry is only safe behind Render's proxy. Run without it, a visitor could set that header to anything.
