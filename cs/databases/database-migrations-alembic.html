🗄️Database migrations with Alembic

How to change the shape of a database step by step, in versioned files, without losing the data already inside.

beginnercs2026-11-27

💡The idea

A database has a schema: the list of its tables, columns and rules. Your Python models (SQLAlchemy classes) describe the schema you want. But a real database already holds users and their data, so you cannot just delete it and rebuild it. A migration is a small file that says how to go from one version of the schema to the next. Alembic runs these files, in order, on every database: your laptop, the tests, production.

💡 Think of it like this

Migrations are like git commits for the database. Each one is a small, named change that points to the one before it. Anyone who replays them in order ends up with exactly the same result.

📖Key words

Schema
The shape of the database: tables, columns, types and rules, but not the data itself.
Migration (revision)
A versioned file with an upgrade() function (apply the change) and a downgrade() function (undo it).
Revision chain
Each migration names its parent in down_revision; the newest one is called head.
alembic_version
A one-row table inside the database that stores the revision it is currently at.
Constraint
A rule the database itself enforces, like "this value must be unique" or "this must point to a real row".

⚙️How it works

  1. Change a model in Python (add a column, a table, a rule).
  2. Generate a migration: alembic revision --autogenerate -m "what changed". Alembic compares your models with the database and writes the difference into a new file.
  3. Read the file. Autogenerate only guesses. A renamed column looks like "drop old column, add new one", which would delete the data in it.
  4. Apply it: alembic upgrade head runs every migration after the one stored in alembic_version, then updates that table.
  5. Undo if needed: alembic downgrade -1 runs the last downgrade(). Add --sql to any upgrade to print the SQL instead of running it, so you can check it first.
⚠️ Common mistake

Running an autogenerated migration without reading it. Alembic cannot tell a rename from "delete + create". Fix it by hand with op.alter_column(..., new_column_name=...).

🔍Example

The habit tracker's first migration, trimmed to one table. It has no parent, so it is the start of the chain.

revision = "0001"
down_revision = None  # first in the chain

def upgrade() -> None:
    op.create_table(
        "check_ins",
        sa.Column("id", sa.Integer(), primary_key=True),
        sa.Column("habit_id", sa.Integer(),
                  sa.ForeignKey("habits.id", ondelete="CASCADE"), nullable=False),
        sa.Column("day", sa.Date(), nullable=False),
        sa.UniqueConstraint("habit_id", "day", name="uq_check_ins_habit_day"),
    )

def downgrade() -> None:
    op.drop_table("check_ins")  # the exact undo

The matching model uses SQLAlchemy 2 style: day: Mapped[date] = mapped_column(Date). Mapped[...] is a type hint that says "this is a database column of this Python type"; no Optional means NOT NULL.

The tests use the real migrations

Before the tests run, they go downgrade base then upgrade head on a test database, exactly like production. A second test compares the models with the migrated database and fails if they differ.

⚖️Why use it

✅ Advantages

  • Existing data survives schema changes.
  • Every database reaches the same schema, by the same steps.
  • Changes are reviewed in git like code, and can be undone.

⚠️ Limits

  • Autogenerate misses renames and some details: you must read every file.
  • One more step each time you touch a model.

🔀Other ways

create_all: fine for a throwaway prototype, but it never changes tables that already exist.
Plain SQL files (Flyway, sqitch): the same idea with hand-written SQL instead of Python.
Framework tools (Django migrations, Prisma Migrate): the same idea built into another framework.

🎯Quiz

  1. The description of a database's tables, columns and rules, without the data, is called its _____.

    Answer

    Schema. The schema is the shape of the database; the rows inside are the data.

  2. Is it true that create_all can add a new column to a table that already exists?

    Answer

    No, false. create_all only creates tables that are missing. It skips existing tables, so the new column never appears. Migrations are needed to change tables that already hold data.

  3. Why should every environment (laptop, tests, production) apply the same migration files?

    Answer

    So every database reaches exactly the same schema by the same steps. Hand-made changes on one machine would make the databases drift apart and cause bugs that only appear in one place.

  4. Which two functions does every migration file contain?

    1. migrate and rollback
    2. create_all and drop_all
    3. upgrade and downgrade
    4. forward and backward
    Answer

    C. upgrade() applies the change and downgrade() undoes it. A sounds right in general, but those are not the names Alembic uses.

  5. Each migration names the one before it, which forms a _____ of revisions.

    Answer

    Chain. The down_revision field points to the parent, so Alembic knows the order. The newest migration is the head.

  6. How does Alembic know which migrations a database has already run?

    Answer

    It reads the alembic_version table inside that database, which stores the current revision id. It then runs only the migrations that come after it in the chain.

  7. What does "alembic upgrade head" do?

    1. Creates a new migration file from the models
    2. Runs every migration not yet applied, up to the newest one
    3. Undoes the last migration
    4. Deletes and recreates all the tables
    Answer

    B. It applies the missing migrations in order and updates alembic_version. A is what "revision --autogenerate" does.

  8. Is it true that adding --sql to an upgrade prints the SQL without changing the database?

    Answer

    Yes, true. This "offline" mode only shows the SQL, so you can check it (or give it to someone) before running it for real.

  9. Why must you read an autogenerated migration before running it?

    Answer

    Because autogenerate only guesses from differences. A renamed column looks like "drop the old column, add a new one", which would delete the data in it, so you fix it by hand.

  10. In SQLAlchemy 2, a column is declared with a type hint like _____[int].

    Answer

    Mapped. Mapped[int] tells SQLAlchemy (and your editor) that this attribute is a database column holding an int; without Optional it is NOT NULL.

  11. Is it true that ON DELETE CASCADE makes the database delete the child rows when their parent row is deleted?

    Answer

    Yes, true. The database itself removes rows that point to the deleted one, for example a user's habits and their check-ins, so no orphan rows are left.

  12. A check-in table has a unique constraint on the pair (habit, day). What does it prevent?

    1. Two habits with the same name
    2. A habit having check-ins on two different days
    3. A check-in that points to no habit
    4. Two check-ins for the same habit on the same day
    Answer

    D. The pair must be unique, so one habit can be checked only once per day. C is the job of the foreign key, not of the unique constraint.

  13. Why store the day a habit was done as a local date instead of a UTC timestamp?

    Answer

    Because what counts is the day in the user's own time zone. A check-in at 23:30 local time could fall on the next day in UTC; a plain date avoids that and makes "once per day" easy to enforce.

  14. Is it true that without a naming convention, you can always predict the names the database gives to constraints?

    Answer

    No, false. Each database picks its own default names. A naming convention gives names like uq_users_email, so a later migration can find and drop the constraint by name.

  15. Why should tests build their database with the real migrations instead of create_all?

    Answer

    So the tests use the same path as production. A broken migration (or a broken downgrade) then fails the tests instead of failing on the real server.

  16. A test compares the models with the migrated database. When does it fail?

    1. When a model changed but no migration was written
    2. When the test database has no rows
    3. When a migration has a downgrade function
    4. When the app has no users yet
    Answer

    A. Any difference between models and migrated schema means a migration is missing. B is not a problem: the test compares the shape, not the data.

🔎Things worth noticing

  • The naming convention in the project only covers indexes (ix) and unique constraints (uq). Foreign keys and primary keys still get PostgreSQL's default names (like habits_user_id_fkey). Adding fk and pk entries would make every name predictable; if you do, read the next autogenerated migration carefully.
  • The "models match migrations" test compares types (compare_type=True) but not server defaults. Changing a server_default in a model without a migration would pass silently.
  • Because the tests go downgrade base then upgrade head, every test run also checks that downgrade() works. Nice.
